# RPA 产品需求共识

更新日期：2026-09-15  
阶段：需求讨论与产品定义

本文整理本轮对话中用户明确确认的需求，并单独列出实现建议和待定问题。历史背景见《影刀相似RPA软件讨论记录-2026-09-15.md》。本文中的候选方案不等同于已经确定的技术选型或已经实现的功能。

## 1. 核心目标

开发支持低代码编排和脚本／程序调用的 RPA 软件。当前主要使用场景是网页查询、数据采集和文件下载。

用户最主要的痛点是自动化运行占用电脑前台、鼠标和键盘。期望自动化尽量在后台执行，用户同时正常使用电脑；必要时短暂切到前台，完成必要操作后回归后台。

## 2. 用户已确认的需求

| 主题 | 已确认内容 |
| --- | --- |
| 使用入口 | 支持低代码编排和向脚本／程序开放接口；当前移除 Agent 使用需求。用户再次明确：实际任务由自研 RPA 程序执行，不由 Agent 逐步代操作。 |
| 主要操作对象 | 网页为主，包括翻页、点击、XHR 响应采集、DOM 读取与解析。网络采集设计同时考虑 fetch。 |
| 浏览器来源 | 接受由软件启动独立浏览器，在其中登录。 |
| 并行执行 | 第一版需要多任务并行，可为并行任务开启多个独立浏览器。 |
| 账号场景 | 第一版按每个网站主要使用一个账号设计，暂不要求同站点多账号管理。 |
| 前后台切换 | 默认后台执行；需要前台而用户仍在操作时，等待键鼠空闲后再自动切换；操作完成后回归后台。 |
| 编排方式 | 同一流程中混合使用可视化步骤和脚本步骤。 |
| 脚本语言 | Python 和 JavaScript／TypeScript 都需要支持。 |
| 复杂网页控件 | 需要处理日期、日期范围、类目及其他下拉选项。 |
| iframe | 存在嵌套 iframe 场景；用户能处理，但希望减少定位和维护的麻烦。 |
| 网站业务数据写入 | 当前不需要上传文件、提交用于新增／修改业务数据的表单，或修改网站业务数据。正常的登录、查询筛选和触发下载仍属于使用场景。 |
| 下载 | 支持自定义保存路径和文件重命名。 |
| 定时执行 | 支持每月、每周、每天及间隔若干天运行。 |
| 停机漏跑 | 运行器恢复后，只补跑最近一次漏掉的计划。 |
| 同流程运行重叠 | 同一流程上一轮尚未结束时，跳过新的计划执行。 |
| 失败处理 | 重试后仍失败时，暂停任务并保留浏览器现场，等待人工处理后继续。 |
| 暂停期间调度 | 同一流程暂停未结束时，后续定时计划也跳过。 |
| 编辑器形态 | 采用纵向步骤列表，用户希望类似影刀的排版 UI；条件、循环等可采用缩进分组的方向。 |

## 3. 调度规则之间的关系

| 情况 | 处理规则 |
| --- | --- |
| 不同流程同时执行 | 允许并行，使用各自的独立浏览器。 |
| 多个任务需要前台 | 按讨论中的执行方向统一排队，并等待用户键鼠空闲后进行前台操作。 |
| 同一流程上一轮还在运行 | 跳过新的定时触发。 |
| 同一流程因失败暂停 | 保留浏览器现场；新定时触发继续按上一轮未结束处理。 |
| 运行器停机，错过多个触发 | 恢复后只补最近一次。 |

应区分“停机漏掉的触发”和“因为已有运行实例而主动跳过的触发”。主动跳过的触发不应自动变成待补跑队列。

## 4. 当前实现建议（尚未作为用户确认的实现规格）

### 4.1 浏览器与任务运行

- 倾向采用可显示窗口的独立浏览器会话，平时后台运行，需要时显示同一会话；具体隐藏、最小化方式需要验证。
- 各浏览器使用独立的用户数据目录，保留各自的 Cookie 等会话数据。网站登录是否持续有效取决于网站本身。
- 浏览器由运行引擎统一管理；可视化步骤与两种语言的脚本通过统一接口操作当前任务的浏览器。
- 前台操作结束或任务失败暂停后释放前台使用权；其他任务继续后台执行。
- 先以“用户仍能正常使用电脑”作为后台执行的验收目标，再验证具体网页和窗口状态。

### 4.2 元素与控件

- 拾取元素时保存标签页、iframe 上下文及目标元素的定位规则。
- 运行时重新解析定位规则；页面或 iframe 重建后重新查找，歧义时给出明确诊断。
- 普通下拉、日期和类目分别采用适合其交互方式的选择动作。
- 下拉入口、弹层选项及最终回填结果分别定位和验证。
- 将可复用的定位规则保存在元素库中，供可视化步骤和脚本共同引用。

### 4.3 数据与下载

- XHR／fetch 采集采用先注册监听、再触发操作、等待匹配响应的顺序；匹配应考虑请求所属页码或筛选条件。
- DOM 采集需要确认目标页面内容已更新，不能仅依赖固定等待时间。
- 跨步骤及跨语言交换结构化数据；原生对象、数据类型边界与序列化规则待定。
- 下载路径和文件名建议支持固定值及流程变量组合。
- 下载步骤在文件实际保存成功后返回最终路径；并行下载应关联到正确的任务。
- 文件同名时的默认策略尚未确认。候选包括加序号、报错或明确配置覆盖。

### 4.4 调度与恢复

- “间隔 N 天”倾向以开始日期为基准计算后续计划，而非从上一轮完成时间重新计时。
- 区分计划执行日期和实际执行日期，补跑时按原计划所属周期计算查询条件和命名变量。
- 失败恢复时先核对页面与已产生的结果，避免重复采集或下载。
- “保留浏览器现场”针对运行器和浏览器仍存活时的暂停；崩溃、重启、断电后的恢复能力尚未确定。

## 5. 编辑器布局建议（待讨论）

已确认的是纵向步骤式编辑方向。以下面板位置和交互方式属于建议：

| 区域 | 建议职责 |
| --- | --- |
| 左侧 | 指令搜索与分类、元素库，通过标签切换。 |
| 中间 | 纵向步骤列表；显示序号、动作、参数摘要和执行状态；条件／循环可折叠并缩进显示子步骤。 |
| 右侧 | 当前步骤的参数、变量引用与输入／输出设置；脚本步骤可打开较大的代码编辑区域。 |
| 底部 | 日志、变量／数据预览、失败截图，通过标签切换。 |
| 顶部 | 保存、运行、暂停／继续、停止等操作；调试操作另行确定。 |
| 任务与计划页面 | 查看并行任务、暂停任务和定时计划，避免所有运行管理信息占满流程编辑区域。 |

建议当前执行步骤和用户正在编辑的步骤采用不同标识。任务失败时，直接展示失败位置、原因和恢复入口。

## 6. 尚需讨论的关键问题

1. **调试能力**：单步、断点、从指定步骤运行各自是否为首版必要能力，以及所需的变量和浏览器状态如何准备。
2. **运行生命周期**：关闭编辑器后运行器是否继续工作，是否需要开机启动，以及计划使用的时区。
3. **异常与恢复细节**：重试次数、可重试动作、暂停恢复位置、人工操作后的状态检查。
4. **前台接管细节**：键鼠空闲的判断时长，前台操作期间用户重新操作时如何处理。
5. **计划边界**：每月指定日期在某月不存在时的处理；不同流程补跑的并发上限。
6. **工程与数据模型**：Runtime 技术栈、流程文件格式、变量作用域、两种脚本的执行方式、开放接口的具体形态。
7. **首次验证样本**：用户已提供拼多多商家后台订单查询页，要求“批量导出”并保存到桌面，作为自研 RPA 的首个业务样本。真实 DOM、导出机制与后台兼容性尚未验证；嵌套 iframe、复杂下拉和分页响应采集另用受控样本补充覆盖。
