## 2. 产品想法：做类似影刀的软件

### 用户

我使用过影刀，我也想写一个与影刀相似的软件，能操作浏览器、鼠标、键盘，不仅可以使用低代码方式，也可放开接口供脚本、agent使用

### 助手

完全可以做，而且你这个定位比“仿影刀”更有意思：低代码 RPA + 可编程自动化内核 + Agent 可调用接口。我会把它设计成三层，而不是一开始就只做一个可视化编辑器。

推荐架构：

1. 自动化内核 Runtime
   - 浏览器控制：基于 Playwright / Chrome DevTools Protocol。
   - 鼠标键盘：Windows 下可用 Win32 API、UI Automation、SendInput。
   - 桌面控件识别：Windows UI Automation、OCR、图像匹配。
   - 文件/Excel/HTTP/数据库/剪贴板等常用动作。
   - 负责执行动作、等待、重试、异常捕获、日志、截图。

2. 流程编排层 Workflow
   - 低代码节点：打开网页、点击、输入、等待元素、读取表格、循环、条件判断、调用接口等。
   - 流程本质建议存成 JSON / YAML，例如：

```json
{
  "steps": [
    { "type": "browser.open", "url": "https://example.com" },
    { "type": "browser.click", "selector": "#login" },
    { "type": "keyboard.type", "text": "hello" }
  ]
}
```

3. 开放接口层 API
   - 给脚本用：Python/JS SDK。
   - 给 Agent 用：REST / WebSocket / MCP 风格工具接口。
   - 给企业集成用：任务队列、Webhook、CLI。

示例：

```ts
await rpa.browser.open(url)
await rpa.browser.click("text=登录")
await rpa.keyboard.type("账号")
await rpa.screenshot()
```

建议的技术路线：

- 后端 Runtime：Python 或 Node.js
- 浏览器自动化：Playwright
- 桌面自动化：Python `pywinauto` / Windows UI Automation / Win32 API
- 前端低代码编辑器：Electron + React Flow，或 Tauri + React
- 流程存储：JSON
- 执行通信：WebSocket，本地服务监听 `localhost`
- Agent 接口：先做 HTTP API，后面再加 MCP 协议会很顺

第一版 MVP 建议只做：

- 可视化流程编辑器
- 浏览器打开、点击、输入、读取文本、截图
- 鼠标移动、点击、键盘输入
- 条件、循环、变量
- 执行日志和失败截图
- 一个脚本 SDK
- 一个本地 HTTP API，供 Agent 调用

等 MVP 跑通后，再加：

- 操作录制器
- 元素拾取器
- OCR 和图像识别
- 定时任务
- 多机器人执行
- 云端编排
- 企业权限和审计日志

关键设计点是：低代码只是 UI，真正的产品核心是一个稳定、可复用、可被程序调用的自动化执行引擎。只要这个内核抽象得好，后面低代码、脚本、Agent、定时任务都只是不同入口。

## 3. 调整定位：砍掉 Agent 使用

### 用户

可以砍掉agent使用，只供低代码、开放接口供脚本、程序使用

### 助手

可以，这个范围更清晰，也更适合先做成产品。

定位可以改成：

低代码 RPA 平台 + 自动化执行引擎 + 脚本/程序调用接口

也就是说，不主打 Agent，而是服务两类人：

- 业务/实施人员：通过低代码流程编辑器拖拽搭建自动化。
- 开发者：通过 SDK、HTTP API、CLI 调用同一套自动化能力。

核心架构可以简化成：

```text
低代码编辑器
    |
流程 JSON / YAML
    |
自动化运行时 Runtime
    |
浏览器控制 / 鼠标键盘 / 桌面控件 / 文件 / Excel / HTTP
    |
SDK / HTTP API / CLI
```

关键点是：低代码流程和脚本接口共用同一个 Runtime。不要为低代码写一套执行逻辑，再为程序调用写一套。否则后期维护会很痛。

流程节点示例：

```json
{
  "steps": [
    { "type": "browser.open", "url": "https://example.com" },
    { "type": "browser.click", "selector": "#login" },
    { "type": "browser.type", "selector": "#username", "text": "{{username}}" },
    { "type": "keyboard.hotkey", "keys": ["CTRL", "S"] }
  ]
}
```

脚本接口也调用同样的动作：

```ts
await rpa.browser.open("https://example.com")
await rpa.browser.click("#login")
await rpa.browser.type("#username", "admin")
await rpa.keyboard.hotkey(["CTRL", "S"])
```

第一版 MVP 聚焦：

- 浏览器自动化：打开网页、点击、输入、等待元素、读取文本、截图。
- 鼠标键盘：移动、点击、输入、快捷键。
- 变量系统：文本、数字、列表、对象。
- 控制流：条件、循环、异常处理。
- 流程编辑器：节点拖拽、参数面板、运行按钮、日志面板。
- 开放接口：本地 HTTP API、JS/Python SDK、CLI。
- 执行记录：日志、截图、失败原因、耗时。

技术上可以用：

- 浏览器控制：Playwright。
- 桌面控制：Windows UI Automation / pywinauto / Win32 API。
- 后端 Runtime：Node.js 或 Python。
- 低代码前端：Electron + React + React Flow。
- 本地通信：HTTP + WebSocket。

砍掉 Agent 后，产品边界会更稳：你做的是一个可视化自动化工具和自动化能力平台。以后如果真要接 Agent，也只是让 Agent 调你的 HTTP API，不需要改变核心架构。

## 4. 要求进一步查资料

### 用户

现在都是泛泛而谈，你先查阅更多资料

### 助手过程摘要

对，这一步应该先把资料扎实一点。我会先看三类资料：影刀/同类 RPA 产品的功能边界、浏览器与桌面自动化的底层技术、以及开源/商业工具的架构取舍。

调研中间结论：

真正难点不是“能不能点击”，而是“元素模型、选择器、等待/重试、前后台执行、录制回放、失败诊断”这些工程层。影刀、Power Automate、UiPath 都在围绕这些东西做产品化包装。

Windows 底层补充：鼠标键盘输入不是简单封装 SendInput 就完事，权限层级、前台窗口限制、UIPI 阻挡都会影响稳定性。这会直接决定运行器是否需要“同权限启动/管理员启动/前台交互模式”。

### 助手最终调研结论

我查了一轮资料，结论比前面要具体很多：你要做的不是“拖拽版脚本工具”，而是一个 RPA Runtime + 元素选择器系统 + 低代码编排器 + 脚本 SDK。

核心发现：

影刀官网强调的能力不只是鼠标键盘，而是“桌面软件、Web 程序自动化”、跨 Windows/Mac/Android/信创系统、积木式搭建、调度、应用市场、指令市场、场景案例库等生态能力。也就是说，影刀真正的产品壁垒在“可复用指令 + 场景模板 + 运行管理”，不只是录制点击。

Power Automate 的资料很值得参考。它把自动化分成 Web UI 元素和桌面 UI 元素，并且明确说明 UI 元素比图像识别和绝对坐标更稳定；桌面侧支持 UIA/MSAA 选择器，Web 侧使用 CSS selector，并支持多个 selector 失败后回退。

浏览器自动化方面，Power Automate 同时支持浏览器扩展和 WebDriver，但 WebDriver 有限制：只能附加到流程启动的浏览器实例，并且物理交互并发时会因为前台窗口要求而出问题。所以产品第一版更建议直接基于 Playwright/CDP 做浏览器核心，而不是先走 Selenium/WebDriver。

Playwright 官方资料显示，它支持 Chromium、Firefox、WebKit，支持 TypeScript/Python/.NET/Java，有自动等待、用户可读 locator、录制生成代码、trace 追踪、截图和 DOM 快照。这个非常适合作为浏览器自动化内核。

桌面自动化方面，Windows 的正路是 UI Automation API。微软文档说明 UIA 可以程序化读取和操作大多数桌面 UI 元素，也用于自动化测试。`pywinauto` 也验证了这个路线，它支持 Win32 和 UIA 两套 backend，可操作 Windows 窗口、控件、鼠标、键盘。

但鼠标键盘底层要小心：Windows `SendInput` 会受 UIPI 权限隔离影响，只能向同等或更低完整性级别的程序注入输入；`SetForegroundWindow` 也不能随便强制抢前台。

调整后的技术判断：

- Web 自动化：Playwright 为主，支持打开、点击、输入、等待、提取、截图、下载、上传。
- 桌面自动化：Windows UIA 为主，MSAA/Win32/坐标点击兜底。
- 元素库：保存 Web selector、UIA selector、文本 selector、截图辅助信息、多 selector fallback。
- Runtime：变量、条件、循环、异常处理、等待、重试、日志、失败截图。
- 低代码编辑器：节点拖拽只是 Runtime 的 UI 外壳。
- 开放接口：HTTP API、CLI、Python/JS SDK 调用同一套动作。

一句话：先做稳定的执行引擎，再做漂亮的低代码编辑器。影刀式产品的根，不在拖拽画布，而在“元素定位、等待机制、失败恢复、运行记录、指令复用”这些硬骨头上。

## 5. 用户认可方向

### 用户

我看了你的见解 都是正确的

### 助手

那太好了，我们已经对准方向了。

我建议下一步别再泛泛聊“架构”，而是落到一份可执行的 MVP 技术蓝图：

1. 第一版产品边界
   明确哪些能力必须做，哪些先不做，比如只做 Windows + Chrome/Edge + Playwright + UIA。

2. Runtime 指令模型
   定义每个动作的 JSON Schema，例如 `browser.launch`、`browser.click`、`ui.click`、`keyboard.type`、`flow.if`、`flow.loop`。

3. 元素选择器模型
   定义 Web 元素、桌面元素、坐标兜底、文本选择器、多 selector fallback。

4. 执行引擎设计
   包括变量作用域、步骤状态、超时、重试、异常分支、日志、截图、调试单步执行。

5. 开放接口
   HTTP API、CLI、Python SDK、JS SDK 怎么调用同一套 Runtime。

6. 低代码编辑器
   节点面板、属性面板、元素拾取器、运行日志、流程调试。

我个人会先从 Runtime 指令模型和元素模型 下刀，因为这两块一旦设计歪了，后面的编辑器、录制器、SDK 都会被拖累。

下一步我可以直接帮你写一版《RPA 软件 MVP 技术方案 v0.1》，包含模块拆分、目录结构、核心数据结构和第一批指令清单。

有，而且挺适合。按 OpenAI Docs 的说法，Skill 本质是把“任务专用说明、资源、可选脚本”打包成可复用工作流，Codex 会在任务匹配时加载完整说明。所以这类长期产品设计任务很适合用 Skill 参与。

建议优先用这几类：

1. `archify`
   用来画 RPA 产品架构图、Runtime 生命周期图、选择器解析流程、低代码执行链路、浏览器/桌面自动化分层图。这个最适合下一步把系统结构落到图上。

2. `ui-design-brain`
   如果要设计低代码编辑器界面，比如节点面板、流程画布、属性面板、元素拾取器、运行日志、调试器，这个很有用。

3. `visualize`
   用来做交互式原型或可视化解释，例如“一个流程从点击运行到失败截图保存”的动态流程演示。

4. `skill-creator`
   建议后面专门创建一个个人 Skill，比如 `$rpa-architect`，以后只要提“继续设计 RPA 软件”，它就按沉淀好的方法输出：竞品分析、Runtime 指令模型、模块拆分、MVP 路线、风险清单。

5. `Context7` 插件
   严格说它不是 Skill，但非常实用。后面查 Playwright、React Flow、Tauri、Electron、pywinauto、FastAPI、NestJS 等最新文档，都可以用它，比凭记忆稳很多。

如果下一步要认真推进，建议组合是：`archify` + `ui-design-brain` + Context7。先用 `archify` 画技术架构和执行流程，再用 `ui-design-brain` 设计低代码编辑器，最后用 Context7 查具体技术栈文档。

### 助手回答

可以。我刚查了，没有安装任何新 Skill，也没有把外部 Skill 用到项目里，只是做候选筛选。

最值得考虑安装：

1. `playwright`
   官方 curated Skill。适合浏览器自动化、页面操作、截图、表单、数据提取、UI 流程调试。和这个 RPA 产品的浏览器内核设计高度相关。

2. `playwright-interactive`
   官方 curated Skill。适合持续调试 Web/Electron 应用，尤其是之后做低代码编辑器原型时，可用它做真实交互和视觉 QA。

3. `cli-creator`
   官方 curated Skill。这个产品明确要“开放接口供脚本、程序使用”，后面设计 CLI / SDK / 本地 API 时很有用。

4. `security-threat-model`
   官方 curated Skill。RPA 涉及鼠标键盘注入、浏览器会话、凭据、文件、系统权限，安全边界很重要。等确定架构后可以用它做威胁建模。

5. `winui-app`
   官方 curated Skill。如果打算做 Windows 原生桌面端，而不是 Electron/Tauri，这个适合 WinUI 3 / Windows App SDK 方向。

外部发现，但建议谨慎：

- `win-computer-use`：一个 Windows 桌面自动化 Skill/工具包，覆盖截图、鼠标、键盘、窗口管理、UIA、图像匹配、OCR、安全急停。非常贴近产品底层能力，但项目很新，安装前应该先审代码。

- `windows-desktop-e2e`：偏 Windows 桌面自动化测试，基于 pywinauto + UIA，适合参考桌面控件定位、稳定 locator、POM、CI 测试体系。

- `UiPath/skills`：更偏 UiPath 生态，不适合直接参与自研 RPA，但可作为竞品能力/术语/流程设计参考。

建议：先安装官方 curated 的 `playwright`、`playwright-interactive`、`cli-creator`。外部 Windows 自动化 Skill 先只参考，不急着装。用户同意后再安装这三个。
